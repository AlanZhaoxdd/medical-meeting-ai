# 《医药会议智能分析平台》演示文稿

> 演示时间：约 12–15 分钟。每一节先写「演示动作」再写「讲解词」；讲解词可直接照着念。

---

## 0. 开场：项目定位与总体架构

**演示动作**：停在登录页，或放一张架构总览图。

**讲解词**：

各位老师好，今天给大家演示的是我们「医药会议智能分析平台」第一阶段——医药会议资料的可审核知识入库与证据检索工作台。

这个项目要解决的问题是：医药企业会召开大量学术会议，每次会议都有原始材料——PDF、PPT、Word 纪要。这些材料里往往藏着重要的医学观点、数据、共识和行动项，但它们是分散的、非结构化的，靠人工整理既慢又容易出错，而且后续想再检索"某个观点是哪次会议、哪一页、谁说的"非常困难。

所以我们搭了这样一套系统，核心流程可以概括成一句话：**保存原件 → 解析 → 标准化 → 语义切块 → 向量化 → 结构化知识提取 → 证据校验 → 人工审核 → 发布 → 混合检索**。

整个系统采用前后端分离 + 微服务式的 Docker Compose 架构，分四层：

- **前端**是 Vue 3 + TypeScript + Element Plus，负责全部人机交互界面；
- **后端**是 FastAPI + PostgreSQL，是唯一的业务事实来源；
- **异步层**是 Celery + Redis，负责耗时的解析、向量化、AI 提取任务，以及一个用 LangGraph 编排的、带"人工审核闸门"的入库流水线；
- **模型层**是独立的模型服务，加载 BGE-M3 向量模型和 BGE 重排模型，还有通过 OpenAI 兼容接口接入的大语言模型做结构化知识提取和问题生成。

这里我想先讲三条贯穿全项目的设计原则，后面每个模块都会反复体现：

第一，**PostgreSQL 是唯一权威，其他存储都只是"缓存"**。MinIO 只存原始文件，Milvus 只存向量和过滤字段，正文永远从 PostgreSQL 回填，并且在回填时再次校验组织、知识库、发布状态。这样即使向量库被写坏或删掉，我们也能从数据库重建，绝不把业务事实放在非权威存储里。

第二，**每一步都幂等、可重试**。上传、切块、向量化、发布、AI 任务，全部带唯一幂等键和版本号；任务失败不会把系统弄成半残状态，Celery Beat 还会每 30 秒自动对账、补投漏掉的任务。

第三，**AI 永远在人的审核闭环里**。AI 只负责提出候选，所有入库内容必须经过证据校验和人工审核才能发布；检索时用户可以一路追溯到原文、页码甚至发言时间段。

下面我按系统页面，从一次完整的会议导入开始演示。

## 1. 登录页

**演示动作**：输入账号密码登录，展示顶部用户信息与角色标签。

**讲解词**：

系统入口是统一的登录认证。技术栈上，密码使用 **Argon2** 哈希存储；登录成功后签发两套 JWT：15 分钟有效的短期 Access Token，和 30 天有效、可轮换的 Refresh Token。Refresh Token 在数据库里只存 SHA-256 摘要，每次刷新都会轮换并撤销旧 token，即使泄露也难以被反查。

更关键的是权限模型。每个用户属于一个组织，角色从低到高是 viewer、reviewer、editor、admin、owner，前端导航、按钮的显隐，以及后端每个接口的读写权限，都按角色统一判定。比如后面大家会看到：viewer 只能看已发布内容，editor 才能编辑纪要，owner/admin 才能彻底删除。整个系统的所有数据都带 organization_id 做租户隔离，一个组织的用户永远看不到另一个组织的数据。

前端这边，路由守卫会在每次跳转前先初始化登录状态，未登录自动引导回登录页，登录后按角色渲染界面。

## 2. 导入会议

**演示动作**：选择知识库 → 选择一个 PDF/DOCX/PPTX 文件 → 展示上传进度和状态流转。

**讲解词**：

这是业务入口：**导入会议**。页面上的上传规则不是写死在前端的，而是进入页面时从后端的 `/meeting-imports/config` 接口拉取——支持哪些扩展名、最大文件多大（默认 50MB），都由服务端配置统一下发，前端和服务端用同一份规则做双重校验。

上传走 `multipart/form-data`，核心亮点是**基于 SHA-256 的去重**。同一个文件再传一次，后端会返回 409 并带上已存在的文档 ID，前端弹出提示让用户选择"关联已有文档继续"还是"查看已有任务"，避免同一份原件在知识库里重复入库。

文件落盘后，后端进入一条**轻量状态机**：UPLOADED → PARSING → EXTRACTING_METADATA → READY_FOR_REVIEW，任何一步失败都可以安全重试或取消。前端每 2.5 秒轮询一次状态，一旦进入"待校对"，就自动跳转到下一节——会议纪要编辑页。

这条流程在设计上有一个刻意的边界：**原始文件先永久保存到 MinIO，解析后的不可变 Block 和一份 DRAFT 草稿立即写入 PostgreSQL**，草稿一就绪就启动"只切块、只向量化"的预向量任务，但**绝不提前创建正式会议或知识项**。也就是说，用户在进入校对页之前，后台已经把正文切好块、把向量算好了，等人工确认后直接复用，体验上几乎感觉不到等待。

解析层值得一提：PDF、DOCX、PPTX 用 **Docling** 统一解析成带结构的 Block；TXT、Markdown 和标准逐字稿 JSON 走我们自己写的确定性解析器，速度更快、结果稳定。对 Word 表格我们做了特殊处理——Docling 会把合并单元格拍平，所以 DOCX 的表格改用 python-docx 无损读取，保留合并单元格结构；同时过滤掉表格在 Docling 里的重复子段落，避免正文重复。

元数据提取也是**确定性的、不依赖 LLM**：从标准会议纪要第一页的会议信息表提取会议名称、会议目的、讨论题目、会议日期、顾问选择标准、参会顾问姓名、内部参会人及原因、记录人这 8 个字段；第三列的政策指引列不进入结构化字段和正文；正文从"具体讨论内容"等分界标题之后开始。

## 3. 会议纪要编辑（校对页）

**演示动作**：展示左侧正文可编辑区域、右侧元数据表单、查找替换、向量化状态和"确认导入"按钮。

**讲解词**：

这一步是人工质量关：**会议纪要校对**。页面上半部分是正文编辑，下半部分是 AI 预填的元数据表单。

设计上最核心的一点是**原始数据与可编辑数据分离**。解析出来的原始 Block 是不可变的，永远不被校对接口更新；编辑操作全部作用在独立的 DRAFT 修订版本上，修订也有自己的版本号。每次 PATCH 都携带 `expected_version`，版本过期就返回 409，绝不覆盖别人的最新修改——这是典型的乐观并发控制。

编辑功能里值得讲的是**查找替换**。全文替换不是简单在前端改字符串，而是在后端一个数据库事务里执行，记录影响到的 Block、完整快照和一次操作 ID；点撤销时，用同一份快照整批回滚。所以用户看到的"替换"是可以事务级撤销的。

元数据表单同样带独立版本号。AI 预填的字段会标 `needs_confirmation`，用户一旦修改就标记为 `user_modified`；提交时带着元数据版本，冲突同样 409。

页面上还有一个直观的"向量化状态"标签：PENDING → RUNNING → SYNCED，正文一旦修改，旧向量立刻标成 STALE。前端调用幂等的向量化接口，带着修订版本号去排队，后台只对"精确版本"执行切块和向量写入；轮询用的是轻量接口，不重复传输整份纪要。这里还用一个**文档级 advisory lock** 把"正文编辑"和"切块/向量写入"串行化，保证旧版本任务不会和新的正文修改交错。

一切就绪后，点击"确认导入"。这个动作要求：带幂等键、当前草稿精确版本已经 SYNCED。确认事务会**冻结当前修订、幂等创建正式会议、把 Document 的 active revision 指向确认稿**，然后从 `extract_knowledge` 开始派发后续入库任务——之前预生成的 Chunk 和向量全部复用，不重复切块、不重复 embedding。哪怕任务派发瞬间失败，会议和确认稿也已经落库，任务保持 QUEUED 由对账器自动补投。

## 4. 基本信息概览

**演示动作**：展示会议列表，按关键词搜索，点击一行进入核验详情。

**讲解词**：

确认导入之后，会议就进入了**基本信息概览**——一个面向后续 AI 分析前置环节的列表页。这里能看到每场会议的名称、日期、领域、地点、参会人数，以及最重要的**核验状态**。

为什么要有一个专门的"核验"环节？因为后面要基于这些会议做 AI 分析，而 AI 分析的质量上限取决于输入信息是否准确。所以系统把"会议基本信息 + 待回答问题"先交给人工确认，确认通过、提交分析之后，内容才被锁定，成为后续分析任务的输入。

列表还承担了旧版会议管理的兼容职责：老的会议列表、新建、编辑路由都重定向到这里，保证历史功能不丢。

## 5. 会议核验详情

**演示动作**：展示会议信息面板、两类问题列表，添加/编辑问题，演示 AI 生成问题 → 证据面板 → 确认 → 提交分析。

**讲解词**：

这是本次演示的重头戏：**会议核验详情页**。

页面左侧是确认过的会议基本信息面板，右侧是问题管理。问题分两类：**切点问题**（cut point，讨论中的关键转折点，比如"专家对某药的定位是否转变"）和**开放性问题**（open ended，比如"某疾病管理存在哪些分歧"）。系统规定两类问题各至少一条才能确认核验。

先看人工流程：用户可以手工添加、编辑、删除问题；问题内容去空白后按"会议 + 类型"做唯一约束，数据库用 partial unique index 保证不重复。所有写操作带 `expected_version` 乐观锁。确认核验后状态变成 CONFIRMED、分析状态 READY；之后如果再编辑任何问题，状态自动退回核验中、分析状态重置为 not_ready——保证"分析输入永远是对应最新内容"。

然后是 AI 环节：点击生成问题，系统创建一个 AI 任务，由一条 **LangGraph 问题生成图**来执行，前端实时轮询进度。这条图有清晰的阶段：

1. **加载会议上下文**：读取确认版纪要、会议信息，校验组织和知识库范围；
2. **生成检索计划**：让 LLM 先规划要查哪些医学实体、研究、药品，并做**接地校验**——计划里出现的实体必须能在会议内容中找到锚点，防止模型编造不存在的议题；
3. **证据检索**：对确认版纪要的切块和知识库已发布内容做混合检索（后面会细讲），候选证据去重；
4. **问题生成**：按结构化 Schema 同时生成切点问题和开放性问题，要求每个问题必须携带真实 chunk 引用和逐字 quote；
5. **程序化校验 + LLM 复核**：程序先检查 Schema 合法、不重复、开放性问题不能是"是否、有没有"这类事实型问题、quote 必须逐字出现在 chunk 原文里；不通过就带着错误信息去优化检索计划，有重试预算；
6. **入库**：再次用 PostgreSQL 权威数据校验证据后写入问题表，状态变为 PENDING_REVIEW，等待人工核验。

页面上的每条 AI 问题都可以展开证据面板，看到它引用的原文段落、以及向量分、关键词分、重排分——**每一个 AI 结论都有据可查**。

可靠性上，AI 任务用 30 分钟租约 + attempt token 防止两个 worker 同时处理同一任务，Celery 失败自动重试，前端持续轮询直到任务落定。

最后，人工确认核验、点击"提交分析"。提交是幂等的，只把会议置为已提交、锁定核验内容，不派发任何任务——因为真正的分析模块在下一阶段，这是为后续留好的接口。

## 6. 知识库管理

**演示动作**：展示知识库卡片列表，新建一个知识库并进入。

**讲解词**：

前面走的会议导入是"会议域"入口，而**知识库**是系统里另一个核心容器：所有文档、知识、模板、检索都挂在某个知识库里。知识库按组织隔离，页面上能看到每个库的文档数和已发布知识数。

删除是软删除——数据不物理消失；只有 owner/admin 可以带 `purge=true` 彻底清除，并且同步删除 MinIO 原件和 Milvus 向量。这是系统里少数不可逆的操作，所以只在显式确认后执行。

## 7. 知识库详情

知识库详情有五个 Tab：文档、知识审核、检索测试、字段模板、设置。先给一个总览，后面每个 Tab 详细讲，遇到专业术语我会当场用大白话解释一遍。

| Tab | 一句话概括 | 后台对应 |
|---|---|---|
| 文档 | 原始材料进来，跑完整个处理流水线 | 文档 + IngestionJob + LangGraph 流水线 |
| 知识审核 | 人工把关 AI 抽出来的知识项 | KnowledgeItem + 审核事件 |
| 检索测试 | 拿真实问题试检索，看证据准不准 | Milvus 向量检索 + PostgreSQL 回填 + 重排 |
| 字段模板 | 配置"每个文档要抽哪些字段" | ExtractionTemplate + 版本冻结 |
| 设置 | 改名、改说明、删除知识库 | KnowledgeBase |

一句话记忆：**文档管"进来什么"，模板管"按什么抽"，审核管"抽出的是否可信"，检索管"能不能找回来"，设置管"怎么维护"**。

### 7.1 文档 Tab：处理管道与实时进度

**演示动作**：上传一份 PDF，展示节点进度条（解析→切块→向量化→知识提取→证据验证→等待审核）。

**讲解词**：

这个 Tab 是知识库的"原料入口"。用户上传 PDF / DOCX / PPTX / TXT / Markdown / 逐字稿 JSON，然后系统自动跑一条入库流水线。我分上传、流水线、进度展示、可靠性四个点讲。

**第一，上传动作。** 前端把文件用 `multipart/form-data` 格式发给后端——可以理解成"一个表单里夹着二进制文件"一起打包发送。后端先算文件的 SHA-256 指纹，SHA-256 可以理解成**文件的身份证号**：内容只要有一个字不同，指纹就完全不同。所以系统能用指纹做去重：同一个文件再传一次，后端返回 409 冲突，前端提示"已有相同原件"，让用户选择复用旧文档，或者勾选"强制新建版本"再入一版。

如果新建版本，文档之间用 `previous_version_id` 连成一条**版本链**——每一版都指向自己的上一版，历史版本永远不可覆盖、永远查得到。

**第二，处理流水线。** 上传成功后后端返回 202（意思是"已受理，正在处理中"）和一个任务编号 job_id，然后一条 **LangGraph 流水线**开始跑。LangGraph 简单说就是**把一段处理流程画成一张图**的编排框架：图上的每个圆圈叫"节点"，代表一步处理；箭头表示执行顺序；图里流转的数据叫"状态"。

我们的图一共 11 个节点，每一步对应进度条上的一段：

`校验原件(8%) → 解析(20%) → 标准化Block(32%) → 构建Chunk(45%) → 向量化(60%) → 知识提取(75%) → 证据校验(84%) → 保存暂存(90%) → 人工审核闸门(92%) → 发布(97%) → 完成(100%)`

其中"**人工审核闸门**"是整个系统最有特色的设计：流水线跑到这一步会主动**暂停**，等人在知识审核 Tab 里把 AI 抽出的知识逐条审完、点发布，图才继续走完最后两步。AI 永远不能自己把内容发布出去。

**第三，为什么能暂停、能重试。** 两个机制：

- **Checkpointer（存档点）**：LangGraph 用 PostgreSQL 做存档，像游戏存档一样，把"跑到哪个节点、中间状态是什么"存进数据库。所以审核暂停、发布恢复，都是从存档点继续，不用从头重跑。
- **幂等键（Idempotency）**：每个有副作用的节点都用"任务ID + 节点名 + 输入版本"拼一个唯一钥匙。**幂等**的意思是"同一操作重复执行一万次，效果跟执行一次完全一样"。比如向量写入这个节点因为网络抖动重试了两次，数据库里也不会有两份重复向量——因为同一个人任务、同一个节点、同一份输入，只允许生效一次。这正是整个系统"怎么失败都不会坏"的根基。

**第四，进度怎么实时显示。** 前端优先走 WebSocket——**WebSocket 可以理解成浏览器和服务器之间的一条"双向对讲机"长连接，服务器可以主动喊话**；而普通 HTTP 请求是"一问一答"，服务器不能主动说话。任务每走完一个节点，服务器就主动推一次消息，所以进度条是实时动的。万一连接断了，前端自动降级成每 3 秒一次的 REST **轮询**——轮询就是"每隔几秒主动问一次"，进度不会丢。

另外两个可靠性设计，讲出来会很加分：

- 同一份文档的"正文编辑"和"切块/向量化"之间，用数据库 **advisory lock（咨询锁）** 串行化。可以理解成数据库提供的一把"业务锁"：大家约定"改这份文档前先抢锁，抢不到就排队"，保证旧版本任务和新编辑不会交错写坏数据。
- 要同步给外部系统的动作（比如"删除某文档的全部向量"）不会直接调用，而是先写进 PostgreSQL 的 **outbox 表**——**outbox 就是"待发件箱"模式：先记一笔账，再由后台任务可靠投递，投完标记已处理**，Celery Beat 每 30 秒对账一次，漏了自动补投。

失败处理也做了收口：某个节点失败，任务进入 FAILED 并带稳定错误码（例如 `llm_completion_limit` 表示模型输出超长），用户可以点重试，从最近的安全节点继续，不需要整条流水线重来。

**术语速查（7.1）**：

| 术语 | 大白话 |
|---|---|
| LangGraph | 把处理流程画成一张图的编排框架，支持暂停、恢复、重试 |
| 节点（Node）/ 状态 | 节点=流水线里的一步；状态=这一步之间传递的数据 |
| Checkpointer | 存档点：把跑到哪一步存进数据库，中断后接着跑 |
| 幂等（Idempotency） | 同一操作重复执行多次，效果和只执行一次完全相同 |
| WebSocket | 浏览器与服务器间的长连接，服务器能主动推送消息 |
| REST 轮询 | 每隔几秒主动向服务器问一次"好了没" |
| SHA-256 | 文件的身份证号：内容变一点，指纹就完全不同 |
| multipart/form-data | 上传文件用的格式：表单字段 + 文件一起打包发送 |
| 202 / 409 | 202=已受理正在处理；409=冲突（如文件已存在） |
| 版本链 | 每版文档指向上一版，历史版本永不覆盖 |
| advisory lock | 数据库的业务锁：同一份数据同时只允许一个任务改 |
| Outbox | 待发件箱模式：先记账、后台可靠投递，同步不丢不漏 |
| 错误码 | 失败原因的统一编号，前端可以据此给用户明确提示 |

### 7.2 切块与向量化设计

**讲解词**（文档 Tab 的延伸讲解）：

刚才流水线里有"构建 Chunk"和"向量化"两步，这是整个检索能力的底座，我单独展开讲。

**切块（Chunking）**：我们拿到的是按结构整理好的段落（Block），但一段话可能太长、模型一次装不下，所以要先切成一块块合适大小的"Chunk"（可以理解成**把一本书拆成方便检索的段落卡片**）。

关键设计是：**不是按固定字数硬切，而是语义切块**。做法是：先用 BGE-M3 向量模型把每个自然段落编码成向量，然后算相邻两段之间的**余弦相似度**——余弦相似度就是把两段文字都变成一串数字（向量），再算这两个向量方向有多接近，接近就是 1，完全无关就是 0。相似度超过阈值 0.65 的段落，说明意思连贯，就合并成一个语义单元；低于阈值就切开。

在语义单元之上，还有 token 约束：目标 700 token、上限 1000 token、相邻块重叠 100 token。**token 是模型处理文本的最小单位**，中文大概一个字算一个 token。重叠 100 的意思是相邻两块之间故意留一点重复内容，防止一句话恰好被从中间切断而丢失意思。大表格单独处理：按行拆、表头保留，不会把一整张大表硬塞进一块。

每个 Chunk 还带一个 **source locator（证据定位）**：来自第几页、第几张幻灯片、哪位发言人、哪个时间段。这就是为什么后面检索结果能精确到"第 12 页、张教授说……"。

**向量化（Embedding）**：把 Chunk 正文交给 **BGE-M3** 模型转成两种向量：

- **稠密向量**：1024 个数字组成的一串，每个数字都有值，擅长捕捉"意思相近"的语义；
- **稀疏向量**：大部分是 0，只记录少数关键词和权重，擅长精确匹配药名、术语这类词。

两种向量都写进 **Milvus**——Milvus 是开源的**向量数据库**，专门干"存向量 + 快速找最相似"这件事。稠密向量用 **HNSW 索引**（一种能在大几十万条向量里秒级找到最近邻居的索引算法），稀疏向量用**倒排索引**（和搜索引擎"关键词 → 文档"的索引是同一个原理）。

最后，每条向量都带 `embedding_version`，比如 `bge-m3-v1@BAAI/bge-m3`。这相当于给向量盖了个"出厂印章"：以后模型升级了，系统能识别出哪些向量是旧模型产的、需要重算，绝不会把新旧两代模型的向量混在一起比较。

**术语速查（7.2）**：

| 术语 | 大白话 |
|---|---|
| Chunk（切块） | 把长文档拆成一段段适合检索和模型处理的内容块 |
| 语义切块 | 按"意思是否连贯"来切，而不是按固定字数硬切 |
| Embedding / 向量化 | 把文字变成一串数字，意思相近的文字在数字空间里距离也近 |
| 余弦相似度 | 用两个向量方向接近程度衡量文字相似度，接近 1 表示几乎一样 |
| Token | 模型处理文本的最小单位，中文约一字一 token |
| 语义单元 | 语义切块先把连贯段落合并成的"候选块" |
| 稠密向量 | 一串全部有值的数字（1024 维），擅长抓语义 |
| 稀疏向量 | 大部分是 0、只记录关键词权重的向量，擅长精确匹配 |
| Milvus | 开源向量数据库，专门存向量、做相似度检索 |
| HNSW 索引 | 一种"最近邻"索引，让几十万条向量里找最相似变成秒级 |
| 倒排索引 | 搜索引擎同款："关键词 → 包含它的文档"的索引 |
| Source Locator | 证据定位信息：页码/幻灯片/发言人/时间段 |
| Embedding Version | 向量的"出厂印章"，用于模型升级后识别并重算旧向量 |

### 7.3 知识审核 Tab

**演示动作**：展示待审核知识项列表，打开抽屉查看原文证据，通过/驳回一条知识。

**讲解词**：

流水线跑到"知识提取"节点时，系统把切好的 Chunk 交给大语言模型（LLM），让它按模板字段抽出结构化知识项：参会人、议题、洞察、共识、分歧、证据主张、证据缺口、行动项。

这里有两个细节值得讲。

一是**结构化输出**。我们不是让 LLM 自由发挥写一段话，而是给它一个严格的 **JSON Schema**——可以理解成一张**"必须照着填的表格模板"**，规定每条知识必须有哪些字段、每个字段什么类型，比如：`item_type`（类型）、`title`（标题）、`normalized_content`（规范化内容）、`confidence`（置信度 0~1）、`source_refs`（证据引用列表）。模型必须输出合法 JSON，程序端还会做解析兜底，防止模型在 JSON 外面夹带解释文字。

二是**每条知识必须带逐字证据**。Schema 里强制要求 `source_refs` 至少一条，每条引用必须包含：真实的 chunk_id（哪个内容块）、block_id（哪个段落）、以及 **quote**——quote 就是**从原文里一字不差抄出来的那句话**，标点都不能改。提取完之后还有一个专门的"证据校验"节点：程序去数据库核对，如果引用的 chunk 或 block 根本不存在，或者 quote 在原文里对不上，整个文档直接判 FAILED，**绝不让没有证据支撑的知识项带病入库**。

知识审核 Tab 就是人工这一环。列表里每条 AI 抽出的知识都是 PENDING（待审核），点开抽屉可以看到：原文证据、页码定位、置信度、它用的是哪个模板版本和哪个模型（这些字段系统都记着）。审核人给三种结论：

- **APPROVED 通过**；
- **REJECTED 驳回**（被驳回的永远不会进入正式检索）；
- **NEEDS_CHANGES 需修改**（审阅者批注修改意见）。

如果审核人直接修订知识内容，状态会自动退回 PENDING，因为它已经不是 AI 原样抽出的那条了，必须重新过一遍审核。整个过程写入 `review_events` 审核事件表，谁在什么时候审的、批注了什么，全部可追溯。

最后是**发布门禁**，四件事缺一不可：① 文档没有任何 PENDING / NEEDS_CHANGES 的知识项；② 每个已批准项都有真实证据引用和逐字 quote；③ 向量已同步（SYNCED）；④ 当前操作者至少是 reviewer 角色。四点全过，点发布，图才从"人工审核闸门"继续走完，批准的知识项和 Chunk 才进入 PUBLISHED 状态，正式可以被检索到。

**术语速查（7.3）**：

| 术语 | 大白话 |
|---|---|
| LLM | 大语言模型，这里负责从文档里抽取结构化知识 |
| 结构化输出 | 强制模型按给定 JSON 格式返回，而不是自由写文字 |
| JSON Schema | 一张"必须照着填"的字段表格：字段名、类型、是否必填 |
| JSONB | PostgreSQL 里存 JSON 的格式，可高效查询和更新 |
| Quote（逐字引用） | 从原文一字不差抄出的证据句，标点都不能改 |
| 证据校验 | 程序核对"引用是否存在 + quote 是否逐字一致"的检查 |
| 置信度（Confidence） | 模型对自己这条抽取结果的把握程度，0~1 |
| 审核状态机 | PENDING→APPROVED/REJECTED/NEEDS_CHANGES，改动会退回 PENDING |
| 发布门禁 | 发布前的硬性检查清单，缺一项就不让发布 |
| Trace（调用链） | 一次模型调用从输入到输出的完整记录，可复盘 |

### 7.4 检索测试 Tab：混合检索

**演示动作**：输入一个医学问题，展示召回结果、四类分数、高亮定位。

**讲解词**：

这个 Tab 是整个平台的价值出口——**证据检索**。注意：检索不生成 LLM 答案，而是返回证据片段和分数，让用户自己判断，保证"每一条结论都可核查"。

整条链路四段式，我一边点一边讲：

**第一段：查询编码。** 用户在搜索框输入一个问题，比如"某药物在二线治疗中的地位"，系统先用 BGE-M3 把这个问题也变成稠密 + 稀疏两种向量——和入库时用的是同一个模型，保证"问的方式"和"存的方式"在一个空间里。

**第二段：混合检索 + 融合。** 在 Milvus 里同时跑两个检索：稠密检索找"意思最像的"（语义召回），稀疏检索找"关键词命中的"（精确召回），各取前 50 条候选。然后两个榜单用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 合并。RRF 的大白话是：**让两个榜单"投票"**——每条候选按它在榜单里的名次获得分数（第一名 61 分，第二名 60 分……两个榜单分数相加），排名越靠前分越高，最后按总分取前 15 条。好处是不用纠结两种检索的分数单位不一样，谁排名靠前谁说了算。

**第三段：回填 + 二次校验（最重要的一段）。** Milvus 返回的只是候选 ID 和向量分数，**正文一律回 PostgreSQL 取**，而且在取的时候再次校验四件事：属于当前组织、属于当前知识库、发布状态是 PUBLISHED、且是文档的最新版本。这一步叫做"回填（rehydration）"，大白话就是**"向量库只负责指路，正文永远回到权威数据库取，并且取的时候再验一遍门禁"**。就算向量库里混进了不该出现的数据，这一关也会把它挡掉。

**第四段：重排（Rerank）。** 前 15 条候选再用 **BGE-Reranker** 做一次精排。重排的大白话：**先用快的检索捞一批候选，再用更精的模型对"查询+候选"逐对重新打相关度分**，最后返回前 5 条。

所以每条结果会同时展示四类分数：`dense_score`（语义分）、`sparse_score`（关键词分）、`fused_score`（融合分）、`rerank_score`（精排分），加上页码/发言人/时间段定位，前端还会把命中的关键词在正文里高亮。

高亮这个小功能也有讲究：中文分词不是简单的按空格切，前端用的是浏览器自带的 `Intl.Segmenter` 中文分词能力，再配合停用词过滤（去掉"的、了、是否"这类没意义的词），才能把"二线治疗"这种术语正确标亮。

可靠性方面：每次检索都会写入 `retrieval_logs` 检索日志表——记录了查询、过滤条件、命中的候选、耗时，这是以后做检索质量评估和审计的原始数据。权限方面，"检索暂存内容"（include_drafts，即还没发布的草稿）对普通用户是隐藏的；即使有人绕过前端直接调 API，后端也会按角色再次拦截——**前端的隐藏只是体验，真正的安全边界在后端**。

**术语速查（7.4）**：

| 术语 | 大白话 |
|---|---|
| 混合检索 | 语义检索 + 关键词检索同时跑，取长补短 |
| RRF 融合 | 两个排序榜单按名次投票合并，不依赖分数绝对值 |
| 回填（Rehydration） | 向量库只给候选 ID，正文回权威数据库取并二次校验 |
| Top-K | 每阶段最多取多少条：召回各 50 → 融合 15 → 精排 5 |
| Rerank（重排） | 先快筛候选，再用更精的模型逐对重新打分排序 |
| Dense / Sparse 分 | 语义相似度分 / 关键词命中分 |
| 高亮 | 把命中的关键词在正文中标亮 |
| Intl.Segmenter | 浏览器自带的中文分词工具 |
| 检索日志 | 每次查询的完整记录，用于质量分析、审计 |
| Include Drafts | 是否检索未发布的草稿内容（角色受限） |

### 7.5 字段模板 Tab

**演示动作**：展示字段列表，新建一个模板。

**讲解词**：

前面说知识提取是"按模板字段抽"，这个 Tab 就是配置模板的地方。

模板本质上是一张**"要抽什么"的清单**，目前内置 8 类字段：参会人、议题、洞察、共识、分歧、证据主张、证据缺口、行动项。新建模板时勾选需要的字段，保存后立即生成 v1 版本。

这个 Tab 的设计重点是**版本冻结**。可以这样理解：**模板像一份"作业要求"，每个文档开始处理时，先把当时的作业要求复印件（template_id + 版本号）钉在这份文档上**。之后模板再怎么改，都只影响新上传的文档，已经跑过和正在跑的任务永远用自己钉住的那一版，结果不会漂移。

而且每一条抽出来的知识项，都会记录三个追溯字段：`extraction_template_id + version`（用的哪版模板）、`prompt_version`（用的哪版提示词，目前是 kb-extraction-v1）、`model_name`（哪个模型抽的）。将来如果发现某条知识有问题，可以一路查回去："这条是 v1 模板 + 第一版提示词 + 某个模型抽出来的"，复盘和追责都清清楚楚。

**术语速查（7.5）**：

| 术语 | 大白话 |
|---|---|
| 提取模板 | "要抽哪些字段"的配置清单 |
| 模板版本冻结 | 任务开始时把模板版本号钉死，之后改模板不影响旧任务 |
| Prompt 版本 | 给模型提示词的版本号，和模板一样参与追溯 |
| Schema | 字段的结构定义（哪些字段、什么类型、是否必填） |
| 可追溯 | 每条知识都能查到"谁、用什么配置、哪个模型抽出来的" |

### 7.6 设置 Tab

**演示动作**：展示知识库名称/说明编辑。

**讲解词**：

设置 Tab 承载知识库的基础维护：改名称、改说明。

这里值得讲的是删除的两个层次，这也是数据库设计里很重要的概念：

- **软删除**：普通删除只是给这条记录盖一个 `deleted_at` 时间戳，数据其实还在数据库里，界面不再显示而已，随时可以恢复；
- **彻底清除（purge）**：只有 owner/admin 角色可以带 `purge=true` 参数真删，并且会**级联清理**——同时删除 MinIO 里的原始文件、Milvus 里的全部向量。级联清理不是直接调外部系统，而是走前面讲的 outbox 待发件箱，保证"数据库删了但向量没删"这种事不会发生。

另外再补一个贯穿全局的概念：**租户隔离**。知识库、文档、知识项、检索日志，所有数据行都带 `organization_id`，后端每个接口都会校验"你只能操作你自己组织的数据"。所以这套系统将来即使部署给多家医药公司共用，各家的数据也是天然隔开的。

**术语速查（7.6）**：

| 术语 | 大白话 |
|---|---|
| 软删除 | 只是打"已删除"标记，数据还在，可恢复 |
| Purge（彻底清除） | 真删 + 级联清掉外部存储，不可恢复，仅 owner/admin 可做 |
| 级联清理 | 删主数据时，把关联的原始文件、向量一并删掉 |
| 租户隔离 | 不同组织的数据用组织 ID 隔开，互相不可见 |
| Organization ID | 每条数据所属组织的标识，权限校验的第一道闸门 |
